# Firebase and deployment setup

The application uses Firebase project `speed-demon-d6581`, Google Authentication and the `(default)` Firestore database. Hosting remains on the existing Vercel and Render services. Source configuration is prepared; backend credentials, deployed indexes and real authenticated writes must be verified by the owner. No production Firebase tests or deployments were performed during implementation.

## 1. Public web configuration

`frontend/config.js` contains the owner's public web configuration, including apiKey, appId, projectId, authDomain, storageBucket and messagingSenderId. Firebase web configuration identifies the app and is intended to be public; it is not an Admin credential. The frontend uses only the official Firebase app/auth CDN modules pinned to 13.0.0, with no bundler or Firestore client SDK. See [Firebase CDN setup](https://firebase.google.com/docs/web/alt-setup).

In Firebase Console → Project settings → Your apps, confirm this web app belongs to `speed-demon-d6581`. In Authentication → Sign-in method, keep Google enabled. In Authentication → Settings → Authorized domains, retain `localhost` and `speed-demons.vercel.app`; the chosen authDomain must also be authorized. Do not enable arbitrary Vercel preview domains. Use `http://localhost:5500` locally; `127.0.0.1` is allowed by the backend but is not in the owner's stated Firebase authorized-domain list.

Sign in and register a permanent username before the host starts to rank. Accounts without usernames may play unranked. Rankings and registered-player names use the username tied to the verified UID, never Google display names or email claims. Signing in or registering after start cannot upgrade that round; signing out, switching accounts, failed replacement-token verification or disconnecting revokes that round's eligibility. One UID can occupy only one player position in a room/round. An ID token verified before start must remain unexpired at the scheduled start. Tokens travel only in private WebSocket JSON over WSS or the profile/registration HTTPS `Authorization: Bearer` header, never URLs, broadcasts or logs. The backend checks Google provider, signature, project/audience, expiry and revocation through [firebase-admin verification](https://firebase.google.com/docs/auth/admin/verify-id-tokens).

## 2. Secure backend credentials

Use an existing dedicated service account where available. It needs `roles/datastore.user` for Firestore and permission to retrieve Firebase Authentication users for revocation checks (for example `roles/firebaseauth.viewer`). Do not give it Owner or Editor merely to run this game. Set permissions using your account; no permissions or credentials are generated by repository scripts.

If you use a service-account JSON key, provision it yourself through your organization's approved process. Upload it directly in the **existing Render service → Environment → Secret Files** as `firebase-credentials.json`. Never paste it into chat or commit it. Render exposes it at `/etc/secrets/firebase-credentials.json`. Set:

| Render setting | Value |
| --- | --- |
| `FIREBASE_PROJECT_ID` | `speed-demon-d6581` |
| `FIREBASE_CREDENTIALS_FILE` | `/etc/secrets/firebase-credentials.json` |

| `PYTHON_VERSION` | `3.13.3` |

You can omit the localhost origins in production if local access to Render is unnecessary. Origins are exact scheme/host/port matches; no wildcards. In an environment supporting Application Default Credentials, omit `FIREBASE_CREDENTIALS_FILE` and set `GOOGLE_APPLICATION_CREDENTIALS` to the private file path (or use an approved workload identity). The application never reads a JSON key from frontend configuration. See [Admin SDK setup](https://firebase.google.com/docs/admin/setup). Do not set `FIREBASE_AUTH_EMULATOR_HOST` or `FIRESTORE_EMULATOR_HOST` on this production backend; initialization refuses these bypasses.

For a manually authorized local integration test, put private credentials outside the repository, set `$env:FIREBASE_CREDENTIALS_FILE` to that absolute path and `$env:FIREBASE_PROJECT_ID` to the intended **test** project. Also replace the public frontend configuration with that test project's web config. Do not use production credentials for automated tests. Existing tests use isolated fakes and need no credentials or Admin installation.

## 3. Firestore rules and index

Keep the current deny-all client rules. `firestore.rules` contains the same policy. All leaderboard reads and writes are performed through the trusted backend; Admin access relies on IAM, not these client rules.

In Firestore → Indexes → Composite → Create index, create:

- Collection ID: `entries`
- Query scope: **Collection** (not Collection group)
- Fields, in order: `score` **Descending**, `achieved_at` **Ascending**, `uid` **Ascending**

Wait until the index is Enabled. `firestore.indexes.json` contains the equivalent index plus an indexing exemption for the historical `rounds.results` array. If the Firebase CLI is already installed, the owner may deploy these definitions with `firebase deploy --only firestore:rules,firestore:indexes --project speed-demon-d6581` from the repository root. This changes cloud configuration; review and run it yourself only when ready. No CLI installation or deployment was performed.

Data layout:

- `rounds/{round_id}`: one completed-round marker, duration, scoring version, scheduled start/end timestamps, start-week key, player count and authenticated results. Guest names, emails, tokens and keys are omitted. Embedded results retain each authenticated player's server-verified score.
- `boards/arithmetic-v3_{duration}_{week-or-all}/entries/{sha256(uid)}`: one best score per UID for each +1-correct/−1-incorrect board. Contains UID, registered username as name, signed score, achievement timestamp and source round ID. Public API returns only names and scores.
- `profiles/{sha256(uid)}`: permanent username, lowercase normalized_username and creation timestamp. Exactly one profile per verified account.
- `usernames/{lowercase_username}`: profile_id of the unique owner. A Firestore transaction reads profile and claim before creating either, with up to five automatic retries. Same-name retries return the original spelling; different-name attempts fail permanently. Names are 3–20 ASCII letters/numbers/underscores, excluding reserved admin/administrator/moderator/system/support. The UI displays "Once registered, your username cannot be changed." beneath the field, requires an explicit acknowledgement, and opens a final dialog showing the exact username before submitting registration.

One transaction reads the completion marker and candidate entries, then creates the round and updates only improvements. All reads precede writes. Reprocessing a completed round cannot count twice, including retries after an ambiguous successful commit. Equal scores keep the earliest completion timestamp, then round ID for the same player; board ordering is score descending, achievement timestamp ascending, UID ascending. Exact tie order is deterministic. A higher score always outranks an earlier lower score.

Weekly board keys use Monday's local date in Africa/Johannesburg (UTC+02:00, no DST). A round belongs to the week of its **scheduled start**, even if it ends after Monday midnight or is persisted later. Current `arithmetic-v3` boards start fresh; no earlier score is carried over. Existing documents are not deleted or migrated. Older pending outbox records keep their own version and cannot populate current boards. Negative best scores are valid. Duration and scoring version are part of the board path, so incompatible scores cannot share a ranking.

No new composite index is needed: the existing score-descending/achieved_at-ascending/uid-ascending entries index applies to the new board paths. Username claims and profiles use direct document reads. The existing Admin service account's Firestore permissions and deny-all client rules cover these collections. No cloud setting, credential, database or authentication provider changes are required. Coordinate backend/frontend release when approved because the profile/username protocol and eligibility rules change; no release or production registration was performed here.

### Nickname protection and controlled account maintenance

The backend reads `usernames/{normalized_nickname}` when guests or signed-in players without usernames create/join rooms, change identity in a room, or start a new round (including replay). Normalization trims nickname whitespace and uses casefold; for registered ASCII names this is the existing lowercase reservation key. Each check costs one point read, including absent reservations. Room entry and round start also refresh each authenticated member profile with one point read, so registrations completed elsewhere use their canonical identity. Guests never write reservations. Slashes and `.`/`..` cannot be verified as document IDs and are rejected; lookup errors fail closed with a retry message. No answer submission reads Firestore.

Lobby messages add `display_name`; guests and authenticated unregistered players appear as `Guest · Nickname`. Results add `display_names` using the round-start snapshot, preserving existing score keys when unique. If a guest and owner temporarily share a raw name, score keys use distinct display names to prevent overwriting. Duplicate display identities are rejected case-insensitively; a logout that would create a duplicate removes that socket from its room. A guest admission check does not permanently reserve a name: another account can claim it immediately afterward. The guest remains visibly distinct, and subsequent identity checks/new rounds reject the reserved nickname until the guest leaves and chooses another. Registration during an active round does not change frozen identity or eligibility. Membership/identity changes during asynchronous start validation cancel that start.

There is no public rename endpoint. Exceptional corrections or account deletion remain an operator-only maintenance task using trusted Admin credentials, outside the public app: record approval/audit evidence, revoke tokens and disconnect the affected account, then transact on its hashed profile and old/new reservations together (verify ownership and new-name availability before writing). For deletion, coordinate Firebase Auth deletion with profile/reservation cleanup; Firestore and Auth are separate services, so use a retryable audited procedure. Historical rounds/leaderboard names require a separately reviewed retention/correction decision. Do not expose this operation through client Firestore rules or weaken registration permanence.

## 6. Free tier and limitations

Firestore's free quota currently includes 50,000 reads and 20,000 writes per day and 1 GiB stored data; check [current Firestore quotas](https://firebase.google.com/docs/firestore/quotas). No Cloud Functions, reset jobs, TTL billing feature or paid infrastructure is required. Each successful authenticated result may update two entries; a round adds one historical document. Up to eight players means at most 17 document writes per transaction, fewer when scores don't improve; retries add reads. Leaderboard queries read at most ten entries and are cached for 30 seconds (failures for 15 seconds), with no frontend polling. Refresh or changing tabs/duration triggers a request. Rankings can lag through cache expiry or database outages.

The local SQLite outbox retries failed writes with capped exponential delays up to five minutes. It survives process restarts **only while its filesystem survives**. [Free Render storage is ephemeral](https://render.com/docs/free): service sleep/restart/redeploy can lose pending records, and there is no promise of zero-loss persistence during an outage on free hosting. Successfully committed Firestore rounds are durable. Disk-full/queue failures are surfaced in round results. Monitor queue size and generic persistence warnings. A persistent disk would require a separate hosting decision; none is provisioned.

Server validation prevents fabricated totals and socket/nickname impersonation. It does not prove that answers were solved by a human; automated solving and coordinated account abuse require a separate anti-cheat policy. Prompt buffering supports latency but cannot make answers arriving after the server deadline count. The browser's timer is advisory and starts relative to the received server time; local network delay can make it trail the deadline. Disconnects end ranking eligibility and do not support midround reconnect; active rooms disappear on backend restart. Limits: eight players per room, 1,000 rooms/active deadline tasks, 2,000 sockets, 80 messages per connection per second, 16 KiB messages and 15 minutes idle timeout. These are abuse bounds, not a guarantee against distributed denial of service.
